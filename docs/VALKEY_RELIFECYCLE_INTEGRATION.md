# AWS Valkey relifecycle integration

## Final runtime contract

The `aws-cache` root owns both Secrets Manager contracts consumed by the
read-only GitOps integration.

```text
/boa/valkey/credentials
├── username = redis
└── password = ephemeral generated value

/boa/valkey/runtime
└── host = module.elasticache.cache_endpoint[0].address
```

GitOps branch `feature/aws-valkey-runtime-integration` reads those fields with
the Secrets Store CSI provider and produces Kubernetes Secret `valkey-secret`
with `host`, `username`, and `password` keys.

The password is generated by `ephemeral.random_password.valkey` and is passed
to Secrets Manager through `secret_string_wo` and to both Terraform-managed
ElastiCache users through `passwords_wo`. Plaintext is therefore not persisted
in Terraform plan or state. `local.valkey_credentials_version` is the single
rotation counter for both write-only destinations.

## Preserved relifecycle structure

- Shared values continue to come from `module.environment`.
- Core VPC and subnet values continue to come from
  `data.terraform_remote_state.core.outputs`.
- The backend remains the existing Seoul S3 backend with state key
  `aws/cache/terraform.tfstate`.
- The provider region and default tags remain based on the shared environment.
- TCP `6379-6380` remains restricted to `private_subnet_cidrs`.
- Cache capacity, snapshot retention, ACL `on ~* +@all`, User Group ID, and
  Serverless Cache name remain unchanged.

## Declarative state migration

The migration does not run `terraform state mv`, `terraform state rm`, or the
`terraform import` CLI command. It does use a reviewed declarative `import`
block for the existing `boa-app` physical user.

| Existing address | Final handling |
|---|---|
| `module.elasticache.aws_secretsmanager_secret.valkey` | `moved` to `aws_secretsmanager_secret.valkey_credentials`; the physical Secret is preserved |
| `module.elasticache.aws_secretsmanager_secret_version.valkey` | `removed { destroy = false }`; immutable old version remains as Secret history while a new write-only version is created |
| `module.elasticache.random_password.valkey` | `removed { destroy = false }`; only the obsolete state entry is forgotten because there is no external object |
| `module.elasticache.aws_elasticache_user.app` | `removed { destroy = false }`, then declaratively imported to `aws_elasticache_user.valkey_legacy`; this re-reads the physical user without carrying the legacy plaintext password into the new state |

Changing the active username from `boa-app` to `redis` requires a new physical
ElastiCache User. Replacing the old address directly would introduce a delete
action and would be rejected by the repository's destructive Apply guard.
Instead, the old `boa-app` address is forgotten without deleting the physical
user and a declarative `import` block attaches that same user to the root
migration address. This avoids the legacy `authentication_mode.passwords`
value surviving an address-only move. The user remains Terraform-managed but
is removed from the active User Group. The reusable module creates
`module.elasticache.aws_elasticache_user.redis`, and the existing User Group is
updated in place to contain only `redis`.

This avoids an orphaned AWS resource and preserves normal `aws-cache` destroy
coverage. If the team later wants to delete `boa-app` before the next complete
cache teardown, that must be a separately reviewed destructive migration; the
normal Apply guard must not be weakened.

## Verified remote plan

The plan was generated with Terraform `1.16.2` against AWS account
`769413326616`, current `aws/cache/terraform.tfstate`, and `-lock=false` after
confirming that no Infra Actions run or cache state lock was active.

```text
Plan: 1 to import, 4 to add, 2 to change, 0 to destroy.
```

| Resource | Planned action |
|---|---|
| Serverless Cache `module.elasticache.aws_elasticache_serverless_cache.main` | no-op |
| Security Group and ingress rules | no-op |
| Existing credentials Secret container | address move only, no-op |
| New credentials Secret Version | create with write-only value |
| Runtime Secret and Secret Version | create |
| Existing `boa-app` User | declarative import to the root migration address plus in-place write-only credential update; imported password list length is zero |
| New `redis` User | create |
| Existing User Group | in-place membership update from `boa-app` to `redis` |

The same JSON predicate used by `scripts/terraform-aws-root.sh` found no action
containing `delete`, so the destructive Apply guard would pass. Re-run the plan
immediately before Apply because remote state and AWS may change after this
inspection.

## Rotation and rollout

Increment `local.valkey_credentials_version` to rotate credentials. The same
ephemeral value is written to Secrets Manager and both managed ElastiCache
users. Apply and the GitOps secret-sync/application rollout should be performed
in one reviewed maintenance window. No application or GitOps repository is
modified by this Infra integration branch.
