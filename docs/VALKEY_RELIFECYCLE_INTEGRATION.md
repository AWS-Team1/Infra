# AWS Valkey relifecycle integration

## Final runtime contract

The `aws-cache` root owns both Secrets Manager contracts consumed by the
read-only GitOps integration.

```text
/boa/valkey/credentials
├── username = redis
└── password = ephemeral generated value

/boa/valkey/runtime
└── host = module.elasticache.cache_endpoint[0].address
```

GitOps branch `feature/aws-valkey-runtime-integration` reads those fields with
the Secrets Store CSI provider and produces Kubernetes Secret `valkey-secret`
with `host`, `username`, and `password` keys.

The password is generated by `ephemeral.random_password.valkey` and is passed
to Secrets Manager through `secret_string_wo` and to the `redis` ElastiCache
User through `passwords_wo`. Plaintext is therefore not persisted in Terraform
plan or state. `local.valkey_credentials_version` is the single rotation
counter for both write-only destinations.

## Preserved relifecycle structure

- Shared values continue to come from `module.environment`.
- Core VPC and subnet values continue to come from
  `data.terraform_remote_state.core.outputs`.
- The backend remains the existing Seoul S3 backend with state key
  `aws/cache/terraform.tfstate`.
- The provider region and default tags remain based on the shared environment.
- TCP `6379-6380` remains restricted to `private_subnet_cidrs`.
- Cache capacity, snapshot retention, ACL `on ~* +@all`, User Group ID, and
  Serverless Cache name remain unchanged.

## Declarative state migration

The migration metadata does not run `terraform state mv`, `terraform state rm`,
or `terraform import`.

| Existing address | Final handling |
|---|---|
| `module.elasticache.aws_secretsmanager_secret.valkey` | `moved` to `aws_secretsmanager_secret.valkey_credentials`; the physical Secret is preserved |
| `module.elasticache.aws_secretsmanager_secret_version.valkey` | `removed { destroy = false }`; immutable old version remains as Secret history while a new write-only version is created |
| `module.elasticache.random_password.valkey` | `removed { destroy = false }`; only the obsolete state entry is forgotten because there is no external object |

These blocks are inert when their source addresses are absent, so they do not
create physical resources on a clean state. The root-owned credentials Secret
and its current version are removed by the normal root destroy, and a later
clean Apply can create them again.

## Clean lifecycle operating model

This branch is not intended to migrate the current live `boa-app` User through
a normal Apply. Destroy the existing Terraform-managed infrastructure through
the reviewed Destroy workflow, then perform a clean Apply from this branch.
The desired configuration contains no `boa-app` resource and no declarative
import block.

A clean Apply creates exactly one active Valkey RBAC User, `redis`, and the
`boa-valkey-users` User Group contains only that user. This keeps repeated
Apply → Destroy → Apply cycles free of migration-only compatibility resources.

## Rotation and rollout

Increment `local.valkey_credentials_version` to rotate credentials. The same
ephemeral value is written to Secrets Manager and the managed `redis`
ElastiCache User. Apply and the GitOps secret-sync/application rollout should
be performed in one reviewed maintenance window. No application or GitOps
repository is modified by this Infra integration branch.
